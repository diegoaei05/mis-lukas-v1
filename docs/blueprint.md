# Project blueprint

How a screen in this app reaches the database. The pattern below is shared. Each module has its own file so this page stays an index.

The product description is in [overview.md](overview.md). Related requirements live in [user-stories.md](user-stories.md).

When a module is built, add `docs/blueprint/{module}.md` and a row in the table at the bottom.

## The shape of a screen

A page is not a Blade template full of HTML. Laravel answers with an Inertia response. React renders the screen. The database is reached only on the server, through Eloquent.

```text
Browser
  → named HTTP route
    → controller (or a Fortify controller, for auth)
      → Inertia::render('area/page', props)     // read
      → action or model → database              // write
        → redirect or validation errors
          → React page under resources/js/pages
```

Pieces that stay the same on every screen:

| Piece | Where it lives | What it does |
| --- | --- | --- |
| Root document | `resources/views/app.blade.php` | First visit only. Loads Vite, the React app, and the page component. |
| Inertia middleware | `app/Http/Middleware/HandleInertiaRequests.php` | Shares `auth.user`, the app name, and sidebar state with every page. |
| Page resolver | `resources/js/app.tsx` | Mounts the React page. Names starting with `auth/` use the auth layout. Settings pages use the app layout plus the settings layout. Everything else uses the app layout. |
| Page component | `resources/js/pages/{name}.tsx` | The screen. `Inertia::render('auth/register')` loads `resources/js/pages/auth/register.tsx`. |
| Route helpers | `resources/js/routes` and `resources/js/actions` | Generated by Wayfinder from the Laravel routes. Forms and links import these instead of hard-coding URLs. |
| Shared props | `HandleInertiaRequests::share()` | Available on every page as `auth.user` and `name`, without each controller passing them. |

Two kinds of request:

1. **First visit** (a normal browser navigation). Laravel renders `app.blade.php`. Inertia boots React and shows the page component with its props.
2. **Later visit** (a link or form from inside the app). Inertia sends an XHR. Laravel returns the page as JSON. React swaps the component. The root document is not reloaded.

Writes follow a second path. The React `<Form>` posts to a route. The controller validates and saves. Success redirects to another Inertia page. Failure redirects back, and Inertia puts the validator messages on `errors` for that form.

`auth.user` is the Eloquent user for the current session. `password`, `remember_token`, `two_factor_secret`, and `two_factor_recovery_codes` are hidden, so they are not in the props sent to the browser.

## What a new module copies

[Accounts](blueprint/accounts.md) is the worked example. For a screen that lists or edits expenditure data, use the same split:

1. A React page in `resources/js/pages/...`.
2. A named route in `routes/web.php`, behind `auth` and `verified` when the screen is private.
3. A controller method that returns `Inertia::render(...)` for the read, with the data the page needs as props.
4. A write path that validates input, then creates or updates an Eloquent model. The page posts through a Wayfinder helper (`something.form()`), the same way registration uses `store.form()`.
5. A migration for the table. The model lists fillable attributes and casts. Hidden attributes stay off the Inertia payload.

Registration is the exception that uses Fortify’s controller. Application screens use controllers under `app/Http/Controllers`.

## Modules

| Module | Summary |
| --- | --- |
| [Accounts](blueprint/accounts.md) | A visitor registers, and a row is written to `users`. |
